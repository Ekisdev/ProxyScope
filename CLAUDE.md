# CLAUDE.md — instructions for Claude working on proxyscope

proxyscope is a local intercepting HTTP proxy (Burp-Suite-like) written in Go, with SQLite storage and a small web UI. See `README.md` for what it is and how it is laid out.

## Mandatory rule: keep README.md up to date

**Any change to the project — new functionality, refactor, relevant fix, new dependency, new flag, new package, changed behavior, important design decision — MUST update `README.md` in the same work turn (and in the same commit if the repo is under git).** Never leave a README update as a pending follow-up. Concretely, update whichever apply: the Status table / "What works now", Known limitations, Configuration (flags), Architecture (package list, dependency direction, request flow), UI API, Database notes, Windows vs Linux section, Requirements, Development, Roadmap. If a change genuinely needs no README edit, say so explicitly in your final message. Also update this file if a convention below changes.

## Intended use

Only for the owner's own traffic or systems with **explicit authorization** to test. Do not add features aimed at unauthorized targets, and keep defaults conservative (loopback binding, no exposure of captured data).

## Phased project — do not work ahead

- **Phase 1 (done)**: plain HTTP proxy, SQLite history, web UI.
- **Phase 2 (done)**: TLS MITM with a custom local CA (`internal/ca`, `proxy/tunnel.go`).
- **Phase 3 (done)**: live intercept (`internal/intercept`, pause points in `proxy.forward`) + Repeater (`internal/repeater`), on the shared `internal/outbound`.
- **Phase 4 (done)**: match & replace rules (`internal/rules`, YAML-loaded, same pause points in `proxy.forward`, before the intercept hold).
- **Phase 5 (done)**: generic TCP/UDP relay (`internal/relay`), as a **separate module**: no dependency on `internal/proxy`, its own listeners/sessions/capture/hold queue.
- **Phase 5.1**: byte-level match & replace rules for the relay. Deliberately not started yet — needs real usage experience with the manual relay against an actual binary protocol first, so don't preemptively design this.
- **Phase 6 (done on Windows)**: system-wide capture via WinDivert (`internal/sysCapture`), removing the need for explicit per-target configuration. Windows-only; Linux gets a compiling, non-functional stub (`capture_linux.go`), not NFQUEUE — see the dedicated subsection below for why NFQUEUE is deferred rather than attempted alongside this phase.

Do **not** implement future-phase functionality unless explicitly asked, even if it looks easy. It is fine (and encouraged) to keep seams for them, e.g. the `proxy.Sink` interface, the schema version in `PRAGMA user_version`. When a phase is implemented, update the README Status table.

## Cross-platform (Windows + Linux/Arch)

The project must build and run on both. Use Go's standard cross-platform APIs (`filepath`, `os/signal` with `os.Interrupt` + `syscall.SIGTERM`, etc.). No CGO (that is why the SQLite driver is `modernc.org/sqlite`). Don't match on errno values (`syscall.ECONNREFUSED` differs on Windows); classify network errors by Go type (`net.OpError`, `net.DNSError`, `net.Error.Timeout()`). If OS-specific code is unavoidable, isolate it in `*_windows.go` / `*_linux.go` files (or build tags), keep it minimal, and document it in the README "Windows vs Linux" section. Through Phase 5 there was none; **Phase 6's `internal/sysCapture` is the first real OS-specific code in this project** (see its subsection under Code conventions below) — it is the reference example for how to isolate and document OS-specific code, not an exception to this rule. Test on Windows when possible; write path handling and shell examples for both OSes in docs.

**Verification status:** Windows is built, tested and run on every phase through Phase 5; Arch Linux was build-tested for Phase 1 only, and Phases 2-5 are only cross-compiled (`GOOS=linux go build`) — Arch verification is deliberately paused and will resume later in the project; don't take that as license to skip cross-compiling or to add anything Linux-specific without flagging it. Don't add platform-specific behavior (syscalls, file locking, path assumptions) without flagging it in the README as unverified on Arch, and keep the README "Verification status per platform" table current. **Phase 6 was run on a real Windows machine on 2026-09-28**: elevated, against a real WinDivert 2.2.2 (64-bit) driver and real TCP traffic through the standalone test server described in the README's "System-level capture", covering handle open/filter acceptance, capture, manual intercept, the TCP same-length constraint (rejection and a successful same-length edit, both confirmed byte-exact end to end), and clean shutdown (driver unloaded, no process left running). That run found and this fixed two real bugs, both with regression tests (see the `sysCapture` and Tests subsections below): a panic on a missing/wrong-architecture `WinDivert.dll`, and a `NOT NULL` constraint violation storing zero-payload TCP control packets. Before this, the code had only ever been cross-compiled and `go vet`-ed for Windows from a non-Windows development environment — keep that history in mind when reasoning about *other* code that hasn't had this kind of real-hardware run yet, but Phase 6 itself is no longer in that state; keep the README's "Verification status per platform" table current with this.

## Code conventions (decided in Phases 1-6)

**Layout**
- Module name and binary: `proxyscope`. Entry point `cmd/proxyscope/main.go` only wires things together; no logic there beyond flag → construct → run → shut down.
- All code under `internal/`. One package per concern: `model` (shared types, no internal deps), `config`, `ca` (root CA + leaf certs), `outbound` (talking to upstreams: transports, timeouts, TLS validation, request building, capture, error classification), `intercept` (hold queue), `rules` (match & replace engine), `proxy`, `relay` (generic TCP/UDP byte relay), `sysCapture` (system-level capture via WinDivert), `repeater`, `store`, `ui`. Don't grow `proxy` into a catch-all; `relay` and `sysCapture` are each a deliberately separate package/concern from `proxy` (and from each other), not a mode of it (see below).
- Dependency direction: `cmd` → everything; `proxy`/`ui`/`repeater`/`relay`/`sysCapture` → `model` (+ `outbound` for `proxy` and `repeater`), plus small interfaces they define themselves (`proxy.Sink`, `proxy.CertIssuer`, `proxy.Interceptor`, `proxy.RuleEngine`, `ui.Store`, `ui.Interceptor`, `ui.Repeater`, `ui.Rules`, `ui.RelayStatus`, `ui.SysCaptureStatus`) which `store.Store`, `ca.Authority`, `intercept.Manager`, `repeater.Service`, `rules.Engine`, `relay.Service` and `sysCapture.Service` satisfy. `store`, `ca`, `outbound`, `intercept`, `rules`, `relay` and `sysCapture` are leaves (at most → `model`; `relay` and `sysCapture` do **not** import `outbound` — neither has HTTP transport/request-building needs). Types that cross these interfaces (e.g. `model.Request`, `model.Outcome`, `model.ErrInvalidRequest`, `model.Rule`/`Scope`/`Condition`/`Action`, `model.Chunk`/`RelaySession`/`RelayChunk`/`RelayTarget`) live in `model`, so `ui` and `proxy` never import `intercept`/`repeater`/`rules`/`relay`/`sysCapture`; `proxy`, `repeater`, `relay` and `sysCapture` never import each other — `sysCapture` declares its own `Sink` interface, structurally identical to `relay.Sink`, rather than importing it from `internal/relay`, to keep the two leaves independent (see the `sysCapture` subsection below). No cycles, no package importing `cmd`. Define interfaces where they are consumed. (Tests may import `ca` to get a real issuer, and `rules`/`intercept`/`relay`/`sysCapture` to get a real engine/manager/service.)
- Frontend is plain HTML/CSS/JS embedded with `go:embed` in `internal/ui/web`. No build step, no npm, no external CDN. One file per view (`history.js`, `intercept.js`, `repeater.js`, `rules.js`, `relay.js`, `syscapture.js`) on top of `core.js` (shared `window.PS` helpers, tabs, detail renderer). Live updates are polling (history 1s, intercept 500ms, relay pending 500ms/sessions 2s, syscapture pending 500ms/sessions 2s), not WebSocket; `rules.js` fetches once per tab entry instead of polling (rules don't change from live traffic, only from explicit user action).
- Anything that lives only in the browser (repeater tabs in `localStorage`) is optional: wrap storage access in try/catch and work without it.

**Naming / style**
- Standard Go: `gofmt` clean (`gofmt -l .` prints nothing), `go vet ./...` clean. Exported identifiers have doc comments; each package has a package comment.
- Constructors are `New(...)`; servers expose `ListenAndServe() error` (returns nil on clean shutdown) and `Shutdown(ctx) error`. Listen inside `ListenAndServe` so bind errors surface immediately.
- Config is a plain struct built in `internal/config` from flags; defaults live in `config.Default()`. Add new settings there and document them in the README table.
- Comments explain *why* (constraints, security, protocol quirks), not what. Keep density similar to existing files.

**Error handling**
- Return errors, don't panic (only exception: `panic(http.ErrAbortHandler)` to abort a half-sent response, and programmer errors on compile-time constants). Wrap with context using `fmt.Errorf("doing x: %w", err)`; compare with `errors.Is/As`. Sentinel errors live in `model` (e.g. `model.ErrNotFound`).
- The proxy must never crash on network errors: map them to a readable plain-text response (`502` unreachable/DNS, `504` timeout, `400` bad request, `501` unsupported), record the error in `Exchange.Error`, and log it. A failed `Sink.Save` is logged, never propagated to the client.
- Logging uses `log/slog` (structured key/value), passed in as `*slog.Logger`; no global loggers, no `fmt.Println` for logs.
- Everything received through the proxy or read back from the database is **untrusted data**: render it in the UI only via `textContent`, never `innerHTML`.

**Proxy engine specifics**
- Use `http.Transport.RoundTrip` directly (not `http.Client`): no redirect following, no cookies, no env proxies, `DisableCompression: true`, so traffic is relayed and stored byte-exact. Strip hop-by-hop headers in both directions. Bodies are streamed and captured through `outbound.Capture` (size-capped); always forward the full body even if capture is truncated. Shared upstream logic (transports, `BuildRequest`, `RemoveHopByHop`, `Classify`, `Capture`, `ReadUpTo`) lives in `internal/outbound`; the proxy and the repeater must both use it so dialing, timeouts and the `-insecure-upstream` behavior can never diverge.
- Store the raw wire bytes; decoding for display (gzip etc.) happens only in `ui/body.go`.
- HTTP and HTTPS share one code path: `forward(w, r, transport)` in `proxy.go`. `tunnel.go` only does CONNECT plumbing (hijack → TLS handshake → per-tunnel `http.Server` → rewrite to absolute `https://` URL → `forward`). Don't duplicate forwarding/recording logic for new transports; extend `forward`.
- Names on an intercepted connection: leaf cert name = SNI, else CONNECT host; upstream address = CONNECT host:port; upstream TLS ServerName = leaf name. Keep it consistent if you touch this.
- Anything that can hang on a peer (TLS handshake, upstream dial/headers) needs a timeout. A failing handshake or invalid SNI must be **logged and recorded** as a `CONNECT` exchange with `Error` set (status 0), never silent.

**Live intercept (`internal/intercept`, pause points in `proxy.forward`)**
- **Pause/resume structure.** There are exactly two pause points, both in `proxy.forward`: (1) after the request is fully received and before `BuildRequest`/`RoundTrip`; (2) after the response is fully received and before anything is written to the client. At each, `forward` computes whether the body must be buffered (`Interceptor.RequestEnabled()/ResponseEnabled()` **or** `RuleEngine.NeedsRequestBody()/NeedsResponseBody()`), buffers it once if so (`outbound.ReadUpTo`, limited by `-max-body`), runs the rule engine (see below; it always runs, buffered or not), and only then, if the matching intercept toggle is on **and** the body was buffered, calls `HoldRequest/HoldResponse`, which mutates the `model.Request`/`model.Response` in place and returns a `model.Outcome` (Verdict, Edited, Note). Anything that transforms traffic at these points operates on the same `model.Request`/`model.Response` objects and reports through `Outcome`/`Exchange` flags the same way; a new pause-point consumer goes **after** rules and **before** the hold, matching this order.
- **No worker goroutines.** The request's own goroutine blocks in `Manager.wait` (a `select` on the item's buffered channel, the timeout timer and `ctx.Done()`). Ownership of an item is decided by removing it from the map under the manager mutex (`take`, `Resolve`, `SetSettings`); only the owner sends on the channel (buffer 1, so it never blocks). Preserve this: a held message must block nothing but its own request, each item is resolved exactly once, and the mutex is never held while sending on a channel or calling out.
- Every hold must end: user action, `-intercept-timeout` (default 60s, 0 = none), client disconnect (`ctx`), toggle-off (`SetSettings` releases), shutdown (`main` releases). New hold paths keep that property.
- The history stores what was **actually sent/delivered** (the edited version) with `req_edited`/`resp_edited`, plus `note` for annotations (auto-forward, not intercepted). A drop is stored as status 403 with `Error`. Messages that cannot be held (body larger than `-max-body`, `text/event-stream`) must stream through unchanged with a note, never truncated (`skipNote` in `proxy.go` builds that note, naming whichever of intercept/rules needed the body).
- `ui/edit.go` is the only place that turns edit forms into model types. Validate everything (method token, http/https URL with a host, header lines, status 200-599); on a validation error answer 400 and leave the item held. Unchanged text bodies keep their original bytes exactly; an edited compressed body drops `Content-Encoding`; CRLF bodies stay CRLF; binary bodies are not editable as text.

**Match & replace rules (`internal/rules`, hooks in `proxy.forward` before the intercept hold)**
- **Where things live.** Rule-definition types (`Rule`, `Scope`, `Condition`, `Action` and their enum types) live in `model`, exactly like `Request`/`Response`/`Outcome` for intercept, so `ui`/`proxy` reference them without importing `internal/rules`. `internal/rules` holds: `rules.go` (small package-local aliases to the `model` types, kept only so this package's own code/tests can spell them unqualified — don't add new fields here, add them in `model`), `compile.go` (validation + one-time regex compilation into an unexported `compiled`/`compiledSet`), `match.go` (scope + condition matching against a `target`), `action.go` (`compiledAction.apply` mutates header/body/status in place), `engine.go` (`Engine`: file I/O, atomic active-set swap, `ApplyRequest`/`ApplyResponse`). A future rule condition/action type is added the same way: a new `model` field/enum value, a `compileCondition`/`compileAction` case, a `matches`/`apply` case, in that order.
- **Compile once, swap atomically.** `Engine` holds the active rule set behind `atomic.Pointer[compiledSet]`; `Load`/`SaveRules`/`SaveRaw` validate + compile a whole new `compiledSet` and only then `Store` it, so a request never observes a half-updated rule set and a failed validation never touches the previously-active one. Regexes (scope path, header/body condition patterns, `body_regex_replace` pattern) are compiled exactly once there, never in `ApplyRequest`/`ApplyResponse`. Keep new rule state inside `compiledSet`/`compiled`, not separate package globals, so the atomic swap stays the only synchronization needed (no mutex, unlike `intercept.Manager`, because there is nothing to block on: `Apply*` never waits on anything).
- **The file is the source of truth**, not SQLite: `Engine.Path()`/`Load`/`SaveRules`/`SaveRaw`/`ReadRaw` are the only ways rules are read or written, and `store` never gets a rules table. A UI save validates first, writes the file (`SaveRules` regenerates YAML from the structured list; `SaveRaw` writes the caller's text verbatim, preserving comments), and only then swaps the active set — in that order, always. A missing file at `Load` is zero rules (not an error); a malformed *existing* file is (both at startup, fatal, and from the UI, `400` with the previous rules kept running).
- **`NeedsRequestBody()`/`NeedsResponseBody()`** are cheap precomputed flags on the active `compiledSet` (true iff some *enabled* rule's condition or action touches the body) that `proxy.forward` checks before deciding whether to buffer at all — keep this precomputation up to date if a new condition/action type can touch the body, or a body-only ruleset will silently stop forcing buffering. `ApplyRequest`/`ApplyResponse` additionally take a `bodyAvailable bool` (true only when the caller actually buffered the body this time) and a rule whose condition/action needs the body **never fires** when it is false — this is what stops an oversized/streaming body from producing a false "rule fired" record while the wire still streams the untouched original.
- **Evaluation**: rules run in `File.Rules` (YAML array) order; every enabled rule matching its own `direction` and scope/conditions applies its one action and is recorded as fired, in order, **before the next rule is evaluated** — so rule N+1's conditions can see rule N's edit. `Apply*` returns the fired rule ids; `proxy.forward` appends them to `Exchange.RulesApplied` (store as JSON, `rule_fired` bool mirrors `len(RulesApplied) > 0` for the cheap history-list flag, schema v3). One action per rule; chain rules for multiple effects on one message.
- **Never touches Repeater.** Like the intercept queue, `repeater.Service` does not call into `rules.Engine` — the repeater bypasses both by design (see below).

**Generic TCP/UDP relay (`internal/relay`, independent of `internal/proxy`)**
- **Not built on `proxy.forward`.** The relay shares no code path with the HTTP engine — it is a separate listener/forwarding loop for raw bytes, because there is no HTTP framing (no method/URL/headers/status/Content-Length) to reuse `model.Request`/`Response`/`outbound.BuildRequest` for. It does share the SQLite store and the general shape of the intercept mechanism, deliberately (see next point). Files: `relay.go` (`Service`, `Config`, `Target` — an alias for `model.RelayTarget`, not a new type, so `ui` never imports this package — `ListenAndServe`/`Shutdown`, `storeChunk`'s capture-cap logic), `tcp.go` (accept loop, per-connection bidirectional `pump`), `udp.go` (per-target datagram loop, per-client-address session map, idle sweep), `hold.go` (the pause/resume mechanism).
- **`holdQueue` in `hold.go` is a parallel mechanism, not a reuse of `intercept.Manager`.** It deliberately copies `Manager`'s concurrency pattern verbatim (no worker goroutine; ownership of a held item decided by removing it from the map under a mutex; the owner sends exactly once on a size-1 buffered channel so it never blocks) operating on `model.Chunk` (`{Data []byte}`) instead of `model.Request`/`Response`. `model.Verdict`/`Outcome`/`ErrPendingGone` are already payload-agnostic and are reused as-is — only the HTTP-typed `HoldRequest`/`HoldResponse` method shapes and `PendingSummary`/`Pending`/`Resolution` (which carry `Method`/`URL`/`Status`) couldn't be reused without either Go-generics-ifying a stable, tested Phase 3 type or stuffing raw bytes into meaningless placeholder HTTP fields — both worse than a second small, typed implementation. Unlike `Manager` (one flat pair of toggles for the whole app), `holdQueue` keys `RelaySettings` **per target name** (`Settings(target)`/`SetSettings(target, ...)`) since each configured target's up/down pause points are independent; one `holdQueue` instance still serves every target, so the UI has one list/poll endpoint, not one per target.
- **One real difference from HTTP intercept, spelled out because it is a deliberate simplification, not an oversight:** `Hold`'s `ctx` is the `Service`'s own shutdown context (cancelled once, in `Shutdown`), not a per-connection one. HTTP intercept gets a live, cancelled-on-disconnect context for free from `r.Context()`; raw TCP/UDP has nothing equivalent, and giving every held chunk its own disconnect-watcher goroutine was judged not worth the complexity for this phase. So a held relay chunk releases on user action, `-intercept-timeout` (the **same** flag/value as HTTP intercept — no separate relay timeout flag), or process shutdown, but not on its specific connection going away mid-hold; `-intercept-timeout` is the backstop. On `ctx.Done()` (shutdown only, here) `holdQueue.wait` forwards unmodified rather than dropping, unlike intercept's `HoldRequest`/`HoldResponse` on client-disconnect — dropping would corrupt a byte stream whose connection is, unlike a gone HTTP client, still alive.
- **Sessions**: TCP session = one accepted connection (opened on accept, closed when either `pump` direction ends — each closes the *other* side's conn on exit to unblock it, standard bidirectional-proxy shutdown). UDP has no connection, so a session = datagrams sharing one client source `ip:port` for one target; the first datagram from a new source dials a dedicated upstream socket for that client (1:1 NAT-style mapping, needed so replies route back correctly) and spawns that session's own downstream reader goroutine. A UDP session's `seq` counter (shared by both directions, for one true chronological history per session) and `bytesUp`/`bytesDown`/`lastActivity` are touched by two different goroutines (the target's one shared inbound reader, and that session's own downstream reader) and so are `atomic.Int64`; the per-direction capture-cap counters (`upCaptured`/`downCaptured`) are each touched by exactly one of those goroutines and stay plain fields.
- **UDP idle eviction is a real background goroutine (`sweepUDPLoop`, one per UDP target), and that is fine.** It is not a "worker goroutine" in the sense the live-intercept "no worker goroutines" rule forbids — that rule is specifically about never letting a *held item* block on something other than its own request/connection. Reaping idle UDP sessions is ordinary resource-lifecycle housekeeping with nothing pausable involved; don't cite the intercept rule against it, and don't apply the intercept rule's ban to future non-hold-queue relay housekeeping either. Sweep interval scales with `-relay-udp-idle-timeout` (`sweepInterval`: `idle/4`, clamped to `[1s, 30s]`) so a short timeout (as in tests) is actually honored promptly and a long one doesn't poll needlessly.
- **Capture cap**: a "chunk" is whatever one `Read()` (≤ `relayBufSize` = 32 KiB) produced — there is no larger framing unit to hold, unlike an HTTP body. `storeChunk` tracks bytes already stored per session **per direction** against `-relay-max-capture`; the full stream is always forwarded regardless, but once the cap would be exceeded, one final row stores whatever prefix still fits (`data`) alongside the real chunk size (`data_size`, so `RelayChunk.DataTruncated()` works exactly like `Exchange.*BodyTruncated()`) with an explanatory `Note`, and no further rows are stored for that (session, direction) — keeping row count bounded on a long-lived session, exactly mirroring `-max-body`'s truncate-but-always-forward philosophy.
- **Hex rendering is shared, not duplicated**: `ui/body.go`'s `hexView` (`hex.Dump` + the `maxHexView` display cap) is used both by `renderBody`'s binary-HTTP-body path and by `ui/relay.go`'s read-only session chunk history. The **held-chunk edit form** uses a different, simpler encoding on purpose — plain `hex.EncodeToString`/`hex.DecodeString` (a continuous hex string, whitespace-tolerant on decode) — because `hex.Dump`'s offset/ASCII-annotated format is display-only and not cleanly reversible; don't conflate the two.
- **Never touches HTTP intercept or the rule engine**, and is never touched by them; `proxy.forward` has no relay awareness and vice versa.

**System-level capture (`internal/sysCapture`, Windows only, independent of `internal/proxy` and `internal/relay`)**
- **Not built on `proxy.forward` or `internal/relay`.** WinDivert hands over raw IP packets with routing metadata, not connections or accepted sockets, so there is no HTTP framing and no relay-style listener/accept loop to reuse either. It shares the SQLite store's `relay_sessions`/`relay_chunks` tables (see Storage below) and the relay's hold/timeout/ownership pattern, deliberately, for the same reasons `internal/relay` shares them with `internal/intercept` — see the relay subsection above for the general rationale; this one only calls out what's different for packets.
- **Files, and which build tag each carries**: `sysCapture.go` (no build tag — `Service`, `Config`, `Sink`, `New`, the accessor methods, `processPacket`: parse → session → hold → capture → return re-injection bytes, `shutdownCommon`), `packet.go` (no build tag — IPv4/IPv6/TCP/UDP header parsing, `flowKey`, `replacePayload`; pure byte manipulation, fully unit-testable without WinDivert), `session.go` (no build tag — `capSession`, the idle sweep, `storeChunk`), `hold.go` (no build tag — `holdQueue`, structurally the same pattern as `relay.holdQueue` but with **flat** `model.RelaySettings`, not per-target, since there is exactly one configured filter in this phase; also where the TCP length constraint is enforced, see below), `capture_windows.go` (`//go:build windows` — `ListenAndServe`/`Shutdown`/`Elevated`, the real WinDivert receive loop), `windivert_windows.go` (`//go:build windows` — the raw `WinDivert.dll` bindings and the `WINDIVERT_ADDRESS` struct layout), `capture_linux.go` (`//go:build !windows` — the stub, see below). Splitting platform-specific code into its own build-tagged files while keeping the packet-processing core (`sysCapture.go`/`packet.go`/`session.go`/`hold.go`) build-tag-free is deliberate: it is what makes `processPacket` unit-testable on Linux with synthetic packets, independent of any real WinDivert handle.
- **The Linux file is a real, minimal, compiling implementation, not a build-tag exclusion.** `capture_linux.go` defines the same `Service` methods (`ListenAndServe`, `Shutdown`, `Elevated`) the Windows file does, so `go build`/`go vet`/`go test` all succeed on Linux and nothing else in the program needs to branch on OS. `ListenAndServe` returns `sysCapture.ErrNotImplemented` (a real, named, checkable error) rather than panicking or silently doing nothing; `Shutdown` still calls the shared `shutdownCommon` (harmless — nothing was ever started); `Elevated` returns `false`. **This is the contract a future NFQUEUE implementation must satisfy too**: same `Service` methods, same `Config`/`Sink` shapes reused where the data fits (see Storage below), its own `*_linux.go` build-tagged file replacing this stub, and the packet-processing core in the build-tag-free files extended (not forked) if NFQUEUE needs something `processPacket` doesn't already do. Do not attempt NFQUEUE by copying `capture_windows.go`'s shape wholesale — NFQUEUE is a fundamentally different API (netfilter/iptables/nftables redirect a packet into a queue before your process ever sees it, rather than your process opening a handle and asking for packets directly the way `WinDivertOpen` does), so its own `capture_linux.go` will look structurally different inside, even though it must expose the same methods.
- **Packet re-injection is this package's responsibility, not WinDivert's.** Diverting a packet takes it out of the normal Windows network stack; nothing delivers it unless `internal/sysCapture` calls `WinDivertSend` itself, with the same `WINDIVERT_ADDRESS` the corresponding `WinDivertRecv` produced (direction/interface metadata WinDivert needs to route it correctly, not just the bytes). Every code path through `processPacket` — forward unmodified, forward edited, drop — must end in either a `Send` call (`capture_windows.go`'s receive loop, for the first two) or a deliberate no-op (drop: never re-injected). Never call `WinDivertRecv` again before resolving what to do with the packet you just got; there is exactly one handle and one receive loop for the whole capture, so a bug here stalls the entire filter's traffic, not just one connection (this is also why holding one packet pauses every other packet matching the filter — see below, and don't try to "fix" that by adding concurrent `Recv` calls without solving packet reordering first).
- **The TCP length constraint is enforced in `holdQueue.Resolve`, not left to the caller.** Re-injection replays the *whole packet*; `packet.go`'s `replacePayload` does same-length in-place substitution for TCP (any length change would desync sequence numbers for the rest of the connection — the same problem any raw-packet MITM has without a full TCP stack) and a length-changing rebuild for UDP (no sequence numbers, so no constraint; the IPv4/UDP length fields and checksums are patched/recalculated). `Resolve` checks the protocol and, for TCP, rejects a length-changing edit with the named sentinel `ErrTCPPayloadLengthMismatch` **before** removing the item from the queue — so the item stays held (mirroring `ui/edit.go`'s "an invalid edit leaves the item held" rule) and the caller can retry, rather than either silently truncating/padding or letting a length-changed packet reach `WinDivertSend` and desync the connection. `ui/syscapture.go` translates this specific error to its own `400` (never folded into the generic `409` a stale/already-resolved id gets) — this distinction has a dedicated test (`TestHoldTCPLengthMismatchRejected` in `internal/sysCapture`, `TestSysCaptureForwardSurfacesTCPLengthMismatchAs400` in `internal/ui`); don't let a future refactor collapse it back into one generic error path.
- **Sessions have no accept()/connection event to key off**, unlike either of the relay's two modes: WinDivert hands over packets, not connections. A session is every packet sharing one 4-tuple (source/destination address+port, protocol) **regardless of direction** (`flowKey` sorts the two endpoints so both directions of one flow hash the same), grouped by an idle timeout generalized from the relay's UDP sweep (`sweepInterval`, same `idle/4` clamped-to-`[1s,30s]` shape, duplicated rather than imported — see the relay subsection's reasoning for why a second small implementation beats a cross-package dependency here too). TCP and UDP are treated identically on purpose: WinDivert gives no more connection-state visibility for TCP than for UDP at the network layer, so building TCP-specific FIN/RST-triggered session closure would be asymmetric complexity for no real benefit in this phase — don't add it without a concrete need.
- **`ClientAddr`/`UpstreamAddr` mean "this machine's own endpoint" / "the remote endpoint"**, not client/server — there is no fixed role at this layer the way the relay's listen/upstream split gives it one. Determined from whichever packet first opens the session: `Outbound` (from `WINDIVERT_ADDRESS`) means `Src` is local; `Inbound` means `Dst` is local.
- **Holding one packet pauses every other packet matching the filter**, mirroring the relay's UDP mode (one shared reader per target) rather than its TCP mode (one goroutine per connection) — there is exactly one WinDivert handle and one receive loop for the whole capture (see the re-injection point above), so this is structural, not a bug to fix. `-intercept-timeout` (shared with HTTP intercept and the relay) is the backstop, same as everywhere else holds exist in this project.
- **`windivert_windows.go`'s bindings are plain `syscall.NewLazyDLL`/`LazyProc` calls against `WinDivert.dll`**, no cgo, matching the Dependencies rule below — this is the same mechanism the Go standard library itself uses for Windows API surface `package syscall` doesn't wrap directly, and the same approach the (archived, MIT) `williamfhe/godivert` binding uses; see Dependencies for why this project wrote its own instead of importing a binding. The `WINDIVERT_ADDRESS` struct layout (80 bytes: 8-byte timestamp, a 4-byte bitfield packing `Layer`/`Event`/`Sniffed`/`Outbound`/`Loopback`/`Impostor`/`IPv6`/`IPChecksum`/`TCPChecksum`/`UDPChecksum`/`Reserved1` LSB-first in that field order, a 4-byte reserved field, then a 64-byte union of which this package only reads the `Outbound` bit) must match WinDivert's C header byte-for-byte — see `windivert_windows.go`'s doc comment for the source. If you bump the targeted WinDivert version, re-verify this layout against that version's `windivert.h` before trusting it; don't assume it's stable across major WinDivert versions (1.x used a completely different, much smaller address struct).
- **Never let a `LazyProc.Call`/`Addr` be the first thing that resolves the DLL.** `syscall.LazyProc.Call`/`Addr` resolve their DLL/proc lazily via `mustFind`/`mustLoad`, which **panic** (not return an error) if the DLL can't be loaded or the proc can't be found — deliberate stdlib behavior for "this must always succeed" APIs like kernel32, but wrong here: a missing or wrong-architecture `WinDivert.dll` (e.g. a 32-bit build of `proxyscope.exe` next to the 64-bit `WinDivert.dll` the README documents — an easy mistake, since a Go toolchain's default `GOARCH` isn't always amd64; `windowsbuilder.bat` now forces `GOARCH=amd64`/`GOOS=windows` explicitly for exactly this reason) is exactly the ordinary, expected-to-happen setup error the "return errors, don't panic" rule above is for, not a programmer error. `winDivertOpen` calls the unexported `ensureLoaded()` first, which calls `LazyDLL.Load()`/`LazyProc.Find()` explicitly — unlike `Call`/`Addr`, these return an error instead of panicking — and caches the result in a `sync.Once`; every other WinDivert call in the file only ever runs after `winDivertOpen` has already succeeded, so they don't repeat the check. Regression test: `TestEnsureLoadedReturnsErrorNotPanicOnMissingDLL` (`windivert_windows_test.go`, Windows-only) calls `ensureLoaded` directly and asserts a normal error, not a panic — it needs neither a real `WinDivert.dll` (true in any environment that hasn't installed WinDivert system-wide, which is why it can run in CI) nor Administrator (only `WinDivertOpen` itself, not loading the DLL, requires elevation).
- **Elevation** (`Service.Elevated`, `capture_windows.go`) uses `golang.org/x/sys/windows`'s `GetCurrentProcessToken().IsElevated()`, not the standard library (`package syscall` has no `IsElevated` helper) and not a hand-rolled `OpenProcessToken`/`GetTokenInformation(TokenElevation)` byte-parse — the latter would be exactly the kind of fragile Win32-struct-layout work `windivert_windows.go` already has to do once, and doing it twice adds risk with no benefit. `-syscapture` without elevation must **log a clear warning and let `WinDivertOpen` itself fail with an explanatory wrapped error**, never crash and never silently do nothing.
- **Never touches HTTP intercept, the rule engine, or `internal/relay`**, and is never touched by them; none of `proxy.forward`, `rules.Engine`, or `relay.Service` has any sysCapture awareness and vice versa.

**Repeater (`internal/repeater`)**
- A direct outbound send through `outbound` only. It must **never** go through the proxy listener, the intercept queue, the rule engine, or the relay, and must use the same `outbound.Config` (timeouts, `-insecure-upstream`) as the proxy. Network failures are stored as results (`Exchange.Error`, status 0), not returned as Go errors; only unusable requests return `model.ErrInvalidRequest`. Results are stored with `Source = model.SourceRepeater` so replayed traffic stays visibly distinct (UI flag, row style, filter). Keep the stored `Content-Length` truthful (`outbound.SyncContentLength`).

**Crypto / certificates (`internal/ca`)**
- All key and certificate code lives in `internal/ca`. Other packages get certificates only through the `proxy.CertIssuer` interface and the public PEM via `Authority.CertPEM()`. **The private key must never leave the package**: no exported accessor, never logged, never written anywhere but `ca.key`, never served by the UI (only `/ca.crt`, public).
- Standard library `crypto/*` only, ECDSA P-256. Validate every name before issuing (`ca.NormalizeName`); reject rather than sanitize.
- CA files live in `<os.UserConfigDir()>/ekisde.dev/Proxy/ca/` (override `-ca-dir`), key mode `0600`, created with `O_EXCL`. Never overwrite an existing CA; refuse inconsistent or expired state with an actionable error.
- Upstream certificate validation is **ON by default**; only `-insecure-upstream` turns it off (and logs a warning). Don't add code that skips verification any other way.
- The code never modifies OS/browser trust stores; the user installs `ca.crt` (steps are in the README). If you change CA behavior, update the README install/rotation sections too.

**Storage**
- SQLite via `database/sql` + `modernc.org/sqlite`, single connection. Schema changes: bump `schemaVersion` (currently 5), add a migration step that runs in its own transaction (see `schemaV5`), never edit an old schema constant, test migrating a real old-version database (`TestSchemaV1DatabaseIsMigrated` through `TestSchemaV4DatabaseIsMigrated`), and document it in the README (including that older versions cannot open the new database). Use parameterized queries only. Match & replace rules themselves are **not** stored here (the YAML file is authoritative, see above); only the fired-rule-ids result of a rule running goes into `exchanges`. Relay **targets** are likewise config-only (`-relay` flags, see `internal/config`), never stored; `relay_sessions`/`relay_chunks` store only what passed through them, in their own tables (not new columns on `exchanges`, since the shape genuinely differs — no method/URL/status). `relay.Sink` (`OpenSession`/`CloseSession`/`SaveChunk`) is `store.Store`'s relay-facing side, mirroring `proxy.Sink`; `sysCapture.Sink` is the identical-in-shape sysCapture-facing side (see the `sysCapture` subsection above for why it's a separate declaration, not an import of `relay.Sink`). **`relay_sessions` gained a `source` column in schema v5** (`'relay'` default vs `'syscapture'`) specifically so sysCapture could reuse `relay_sessions`/`relay_chunks` instead of getting its own tables — the two engines produce the exact same shape (raw bytes, direction, session, timestamp), and `source` is the discriminator, the same pattern schema v2 used for `exchanges.source`. `store.ListRelaySessions` takes a `source` filter (empty = every source) precisely so the Relay tab and the System Capture tab each see only their own sessions (`ui/relay.go`/`ui/syscapture.go` hardcode their own source, never client-controlled) despite sharing one id sequence and one pair of tables. A sysCapture session's `target` column holds the capturing filter string, not a configured relay target name — don't assume `relay_sessions.target` always names a `-relay` target. **`store.SaveChunk` normalizes a nil `RelayChunk.Data` to a non-nil empty `[]byte{}` before binding** (`append(nil, emptySlice...)` returns nil, not an empty slice, and `database/sql` binds a nil `[]byte` as SQL `NULL`, which violates `relay_chunks.data`'s `NOT NULL`) — sysCapture hits this routinely (a bare TCP ACK/SYN/FIN has a zero-length payload, and WinDivert hands over every packet matching the filter, not just ones carrying data), relay's own chunks never do (a successful `Read()` never yields a nil/empty buffer), but the fix belongs at this one shared insertion point regardless of which caller triggers it.

**Tests**
- Concurrency code (`intercept`, `relay`'s and `sysCapture`'s `holdQueue`, the pause points) needs tests that run under `-race`: many simultaneous held items resolved out of order, timeout, disconnect/shutdown release, release on toggle-off. Wait with deadlines (`waitHeld`/`waitPending`-style polling), never with fixed sleeps as assertions.
- Table/behavior tests next to the code (`*_test.go`), using `httptest` for the proxy (`httptest.NewTLSServer` + `Config.UpstreamRootCAs` for HTTPS upstreams), real loopback `net.Listen`/`net.ListenUDP` sockets for `relay` (there is no httptest equivalent for raw TCP/UDP), and `t.TempDir()` for SQLite, CA and rules-file directories. Tests must never touch the real user CA/rules directory or OS trust stores. New behavior needs a test. Rule validation needs a table test naming the exact substring expected in the error (see `internal/rules/rules_test.go`'s `TestValidationErrors`), not just "an error occurred". `internal/relay`'s tests construct a `Service` directly and poll `Service.Addr(target)` until bound (needed because tests bind to `:0` for a free port) rather than assuming a fixed port. `internal/sysCapture`'s tests drive `Service.processPacket` directly with hand-built synthetic packets (`buildIPv4TCP`/`buildIPv4UDP` helpers in `packet_test.go`) rather than a real WinDivert handle — this is what makes the package's core logic testable at all on a non-Windows machine; a change to `processPacket`, `packet.go`, `session.go` or `hold.go` needs a test that runs this way, and a change that can genuinely only be exercised through a real WinDivert handle must say so explicitly (in the PR/commit message and the README's Verification status table) rather than being silently left untested. A rejection path (like the TCP length-mismatch constraint) needs its own dedicated test asserting the specific sentinel error, not just "an error occurred" — same bar as rule validation above. Two regression tests came out of Phase 6's first real Windows run (2026-09-28, see "Verification status" above): `TestEnsureLoadedReturnsErrorNotPanicOnMissingDLL` (`internal/sysCapture/windivert_windows_test.go`, Windows-only) for the DLL-load-must-not-panic contract, and the nil-`Data` case added to `TestRelaySessionAndChunkRoundTrip` (`internal/store/store_test.go`) for the `SaveChunk` `NOT NULL` fix — both pin down bugs that were invisible to `fakeSink`-based/in-memory tests (neither a lazy-DLL panic nor a real `NOT NULL` constraint exists in a fake), which is exactly why they were missed before a real Windows + real SQLite run; don't remove either without understanding why they're there, and don't assume an in-memory fake sink is sufficient coverage for something that ultimately talks to a real OS DLL or a real database constraint. Run `gofmt -l . && go vet ./... && go test ./...` before finishing a change, **and, for any change touching `internal/sysCapture`'s `*_windows.go` files, also `GOOS=windows GOARCH=amd64 go build ./... && GOOS=windows GOARCH=amd64 go vet ./...`** (most development on this project happens from a non-Windows environment that cannot run `go test` for that code, but it can and must still compile and vet cleanly; when you *are* working from a real Windows host, as in the 2026-09-28 verification above, actually run `go test ./internal/sysCapture/...` there too rather than settling for build+vet).

**Dependencies**
- Prefer the standard library. Adding a dependency needs a reason, a README mention (Requirements/Architecture), and must not require CGO. Current exceptions: `modernc.org/sqlite` (no CGO SQLite driver), `gopkg.in/yaml.v3` (rules file parsing; no YAML in the standard library), and `golang.org/x/sys/windows` (Phase 6, Windows-only elevation check via `GetCurrentProcessToken().IsElevated()` — the standard library's `syscall` package has no equivalent; this was already a transitive dependency via `modernc.org/sqlite` before Phase 6 made it a direct one, so it added no new module or `go.sum` entry). `internal/relay` added no new dependency: it is `net` (stdlib) only. **`internal/sysCapture` added no new WinDivert *binding* dependency either**: it talks to `WinDivert.dll` directly via `syscall.NewLazyDLL`/`LazyProc` (see the `sysCapture` subsection above) rather than importing a third-party Go binding, because the realistic options at the time were an archived/unmaintained one (MIT) or a GPL-3.0 one (which would have forced copyleft licensing onto this project) — check license and maintenance status again before ever reconsidering that choice, and prefer extending this project's own small wrapper over adding one.

## Workflow checklist for every change

1. Implement (only the requested phase/scope).
2. `gofmt -l .`, `go vet ./...`, `go test ./...`; if the change touches `internal/sysCapture`'s `*_windows.go` files, also `GOOS=windows GOARCH=amd64 go build ./...` and `GOOS=windows GOARCH=amd64 go vet ./...`.
3. Update `README.md` (and this file if conventions changed) **in the same turn**.
4. Don't commit binaries or `*.db` files (see `.gitignore`).
